# AGENTS.md — правила работы агента в этом репозитории

Инструкция для ИИ-агентов (Codex/Copilot/opencode и т.п.), работающих с этим проектом.
Сначала читать целиком, потом работать. Сомневаешься — спроси пользователя, не изобретай.

## Что это за репозиторий

Полигон проекта распознавания речи: рабочий MVP-прототип (MVP) + документы на следующее
приложение «Расшифруй» (создаётся с нуля). Основные документы (читать перед работой):

- `PROJECT.md` — факты, замеры, полный опыт прототипа (источник правды по прошлому);
- `PROMPT_APP_V2.md` — задание на реализацию v2 (эпики, решения, критерии приёмки);
- `APP_V2_DESCRIPTION.md` — описание целевого приложения;
- `MODEL_CORE.md` — описание ML-ядра (ASR, диаризация, сборка реплик).

## Жёсткие требования продукта (нарушать нельзя)

1. **Полный офлайн**: запрет передавать аудио внешним сервисам; запрет облачных API для
   транскрибации/диаризации/обработки текста; запрет вычислений на удалённых серверах.
   В коде не появляются `INTERNET`-permission, OkHttp/Retrofit, Firebase, аналитика, crashlytics.
2. **Без подмены модели**: `text` в результате — только вывод ASR; никогда не зашивать
   «эталонные» расшифровки, не подставлять заготовки «чтобы тест прошёл».
3. Java-only (без Kotlin в логике), UI в XML без Compose, тема Material 3.
4. Логи приложения везде `Log.d("GigaAMTest", …)`.

## Безопасность при подготовке к Git (важно, делаем с расчётом на последующий push)

- **Большие бинарники — не в обычный git.** Файлы моделей (`*.onnx`, ~224 МБ) больше лимита
  GitHub (100 МБ). Перед первым push: подключить **Git LFS** для `*.onnx`, `*.aar`,
  тестовых аудио (`*.ogg`, `*.wav`) — либо исключить их из репо и приложить скрипт скачивания.
  Не коммитить 200+ МБ в обычный коммит — это сломает репозиторий.
- **Не коммитить**: `local.properties`, `*.jks`/keystore/пароли, сгенерированные `build/`,
  `.idea/` (кроме общих конфигураций), конфиги с секретами, записи с микрофона и личные аудио.
- В коде и тест-данных **не оставлять личные пути** (`C:\Users\Daniil\…`) — использовать
  относительные пути/Gradle-DSL.
- Записи и расшифровки — персональные данные: их в коммитах и тест-фикстурах не хранить
  (тестовый ассет `ru_long_consonants.ogg` — публичный Wikimedia-файл, ok).
- Перед коммитом проверить diff глазами: нет ли ключей/токенов/URL, которых там быть не должно.
- Целевая ветка и push — только по явному указанию пользователя; самовольно пушить нельзя.

## Технические грабли, которые агент обязан уважать (подробности — в PROJECT.md)

- `noCompress += "onnx"` в Gradle обязателен.
- `OfflineRecognizer` создавать с assetManager = `null` (модель в приватных файлах).
- BPE-токены склеивать без добавленного пробела (префикс `▁`).
- Лимит модели ~200 с → рабочий лимит 180 с (TODO-чанкинг).
- Для файлов — даунмикс в моно + ресемпл в 16 кГц своим кодом (MediaCodec конверсию не делает).
- Запись микрофона — `AudioRecord` сразу 16 кГц моно (resample не нужен).
- NNAPI готового AAR не работает (issue #2073) — не тратить время, провайдер cpu.
- Кластеризация реплик с диаризацией — только по токенам (слова не рвать).
- `connectedDebugAndroidTest` удаляет APK+данные; тесты с состоянием — вручную
  (`adb install -r -t` + `am instrument`).

## Дисциплина изменений

- Не отключать/не ломать существующие тесты MVP; новые писать под критерии приёмки из
  `PROMPT_APP_V2.md`.
- Очередь «вне скоупа v2» (чанкинг, потоки, префетч, антиалиасный ресемплер, своя sherpa-сборка,
  fp32, QNN) — не реализовывать без явной просьбы.
- **LLM после ASR — запланировано (2026-11-07), но НЕ в v2**: этап «TextPolisher» — локальная LLM
  на устройстве проверяет пунктуацию и исправляет смысл/опечатки в готовой расшифровке.
  Рамки: только локально (облако запрещено ТЗ), `start_ms/end_ms/speaker_id` не меняются,
  текст остаётся в каноничной схеме, исходный ASR-вариант дублируется в лог; сама LLM-модель
  (мульти-гигабайты) в репозиторий не попадает — LFS или download-механизм. Не реализовывать
  без явной просьбы.
- После ощутимых изменений синхронизировать документацию (`PROJECT.md`, `PROMPT_APP_V2.md`,
  `APP_V2_DESCRIPTION.md`, `MODEL_CORE.md`) — как минимум отметить факты, которые менялись.
- Новый код сопровождается комментарием «зачем», а не «что»; комментарии — по-русски
  (как в прототипе), терминология и названия классов — по-английски.
- Ошибки сборки/тестов чинить в месте «что сломано», а не маскировать длинными try-catch/pass.

## Стиль коммуникации

- Отвечать по-русски, кратко, с чем согласен/не согласен и почему;
- перед реализацией крупного — кратко перечислить план и получить «ок»;
- численные замеры писать с единицами (мс/с) и условиями (эмулятор, потоки).
