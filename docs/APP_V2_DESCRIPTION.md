# «Расшифруй» от meevo — описание приложения

Офлайн-приложение для Android: записанный или выбранный звук превращается в расшифровку
с таймкодами и с указанием, **кто из говорящих какую реплику произнёс**.

Приложение создаётся с нуля. Вся обработка выполняется исключительно на устройстве:
сеть не используется ни на каком этапе — это не просто особенность реализации, а жёсткое требование.

---

## 1. Возможности

| Функция | Описание |
|---|---|
| Загрузка аудиофайла | Кнопка «Добавить файл»: минимум `.mp3` и `.wav`, плюс файлы, которые умеет MediaCodec (`.ogg`, `.flac`, `.m4a` — поддерживаются, сообщаем по факту). Перед обработкой файл проверяется (формат/читаемость/длительность) |
| Запись звука | Кнопка-иконка микрофона: первое нажатие — начало записи, второе — окончание и передача записи в пайплайн. Право `RECORD_AUDIO` запрашивается при первом нажатии |
| Распознавание | GigaAM v3 RNN-T через sherpa-onnx: текст реплики плюс таймстемпы каждого токена |
| Разделение говорящих | Всегда включена: каждый интервал речи получает свой номер спикера |
| Вывод результатов | Полная расшифровка со списком реплик и временными метками |
| Экспорт | Кнопка «Экспорт» внизу: формат TXT (позже JSON/SRT поверх той же модели данных) |

Названия и подписи в интерфейсе: заголовок **«Расшифруй»**, под ним — **«от meevo»**.

---

## 2. Экран (Material 3)

Сверху вниз:

1. Заголовок «Расшифруй» + подпись «от meevo»;
2. Ряд действий: кнопка **«Добавить файл»** и кнопка-иконка **микрофона**; под ними —
   **одна строка статуса** для всех событий (имя загруженного файла / «Загружается…» /
   «Записывается… 00:xx» / «Подготовка модели…» / «Декодирование…» / «Распознавание…» /
   «Диаризация…» / «Готово» / «Ошибка: …»);
3. Окно результатов фиксированной высоты с внутренней прокруткой — контент длиннее окна
   прокручивается внутри, экран не тянется;
4. Кнопка «Экспорт» (недоступна, пока нет результата).

Кнопки ввода и «Экспорт» недоступны, пока идёт распознавание; во время записи недоступна
и кнопка «Добавить файл». Очереди заданий нет: параллельный второй запуск не выполняется.

---

## 3. Архитектура (3 слоя)

Продуманный принцип: ни один слой не знает про остальные больше, чем нужно; обмен — только
через каноничный список реплик.

```
┌ UI-слой: MainActivity + Material-компоненты ─────────────────────────────┐
│   только отображение статуса/результатов и приём пользовательского ввода   │
│                 │ (подписка)        ▲ (события статуса)                │
├─────────────────▼─────────────────│──────────────────────────────────────┤
│ Управление (Application-scoped синглтон)                                  │
│   • владеет моделью и распознаванием;  • фоновый поток;                   │
│   • состояния: IDLE / PREPARING / DECODING / RECOGNIZING / DIARIZING /    │
│     DONE / ERROR                                                          │
├─────────────────▼────────────────────────────────────────────────────────┤
│ Данные (пайплайн распознавания, у синглтона)                              │
│   декод (MediaCodec → PCM исходной частоты/каналов)                       │
│   → даунмикс в моно + ресемпл в 16 кГц (наш код, декодер этого не делает) │
│   → ASR (sherpa-onnx OfflineRecognizer: текст + таймстемпы токенов)       │
│   → сегментация (Segmenter: реплики по паузам/знакам к. предложения)      │
│   → слияние с диаризацией (OfflineSpeakerDiarization)                     │
│   → каноничная модель реплик                                              │
└───────────────────────────────────────────────────────────────────────────┘
```

- **Ключевое свойство:** распознавание не привязано к Activity. Пока приложение открыто,
  начатая обработка **всегда доводится до конца** — поворот экрана/пересоздание Activity
  на неё не влияет. Останов происходит только при закрытии приложения.
- **Инициализация модели** — в фоне после первого `onResume`: копирование файлов модели
  из assets (~7 с на 224 МБ) и создание сессий распознавания; в статусе выводится «Подготовка модели…».

### Модель данных реплики (единая для всего)

```json
{
  "transcript": [
    { "speaker_id": "speaker_1", "start_ms": 1250, "end_ms": 4380, "text": "Добрый день!" }
  ]
}
```

- `speaker_id` — `speaker_<N>`; `start_ms`/`end_ms` — целые миллисекунды; `text` — результат модели.
- **Этот вид — внутренняя модель приложения**, а не просто экспортный формат: UI, логи,
  экспорт TXT/JSON/SRT строятся из такого списка. Секунды → миллисекунды конвертируются ровно
  один раз, при формировании списка.
- Время на экране и в экспорте — **единый формат `mm:ss.ss`**, одна функция-форматтер;
  JSON хранит только целые миллисекунды.
- Полный результат дополнительно дублируется в лог `Log.d("GigaAMTest", ...)`.

### Финальный анализ: `TranscriptAssembler` (кто + что → обобщённая расшифровка)

Конвейер заканчивается шагом-анализом, который складывает **две независимые структуры**:

- **ЧТО говорят** — токены ASR с таймстемпом начала каждого (из `OfflineRecognizer`);
- **КТО говорит** — интервалы активности спикеров (из `OfflineSpeakerDiarization`).

и выдаёт **одну обобщённую структуру** — каноничную список реплик. Каждому токену,
через перекрытие его таймстемпа с интервалом спикера, присваивается текущий говорящий;
смена спикера закрывает реплику и начинает новую; текст каждой реплики собирается заново
из её токенов (слово разорваться не может), а её границы — это первый и последний токен.
Компонент — чистая функция над двумя входами, без зависимости от UI и sherpa, с unit-тестами.
Кластеризация спикеров (по порогу, объединение кластеров при более чем 5 спикерах) — часть
шага диаризации до ассемблера: на его вход приходят уже готовые интервалы `speaker_N`.

Порядок наращивания новой разработки: MVP-ядро (файл → расшифровка) → запись с микрофона →
экспорт → диаризация.

## 4. Ограничения и допущения

| Ограничение | Значение |
|---|---|
| Офлайн | Аудио **никогда не** покидает устройство: никаких облачных сервисов распознавания/диаризации/обработки текста, никаких «зашитых» ответов вместо модели |
| Длительность | Единый лимит **180 с** для файла и записи (запас до модельных ~200 с). Длиннее — отказ «длиннее 3 минут пока не поддерживается»; это снимется чанкингом, помечено как будущий MVP-этап. Запись с микрофона останавливается автоматически на 180 с |
| Формат записи | `AudioRecord` 16 кГц моно 16-bit — родной формат модели, ресемпл не нужен. Для файлов — даунмикс в моно + ресемпл в 16 кГц средствами приложения (декодер этого не делает) |
| Устройства | Смартфоны с ОЗУ более 4 ГБ (модели ~224 МБ ASR + 30–70 МБ диаризации), диалогов «не поддерживается» не показываем |
| Хранение записей | Только в приватном каталоге приложения (`cacheDir`), наружу не пересылаются |
| Язык | Только русский (модель русскоязычная) |

## 5. Стек и модели

- **Язык**: Java; UI — XML без Compose; тема Material 3.
- **Движок**: sherpa-onnx (AAR v2.0.1, файлы лежат в `app/libs`). Нативная библиотека
  уже содержит нужные API: распознавание (`OfflineRecognizer`) и диаризацию
  (`OfflineSpeakerDiarization`). Без сети, без облачных сервисов.
- **Модели** (кладутся в assets, в момент сборки; на устройстве копируются в приватную папку):
  - основной ASR: `csukuangfj/sherpa-onnx-nemo-transducer-punct-giga-am-v3-russian-2025-12-16`
    — `encoder.int8.onnx` (~224 МБ), `decoder.onnx`, `joiner.onnx`, `tokens.txt`;
  - диаризация: pyannote-сегментация (~2–3 МБ) + speaker-embedding модель (~20–70 МБ;
    например 3D-Speaker или TitaNet).
- Пакет (`applicationId`): `ru.meevo.rasshifruy`.
- **minSdk 26** (решение 2026-11-07); targetSdk фиксируется при планировании.
- Разрешения: только `RECORD_AUDIO`; SAF-пикер и экспорт прав на хранение не требуют.
- R8/ProGuard полностью отключены (`minifyEnabled false`) — защита нативного JNI-слоя sherpa от искажений оптимизатором.

## 6. Известные технические особенности (вынесены из проверенного прототипа)

- Шаг таймстемпов ≈ **40 мс**; модель отдаёт начало каждого BPE-токена (без длительностей).
- Лимит ~5000 кадров навсегда фиксирует ограничение 200 с на один прогон аудио.
- BPE-токены: слова склеиваются без добавленного пробела (пробел несёт ▁-префикс токена).
- ONNX-файлы в assets должны быть помечены `noCompress`.
- Класс распознавателя создаётся **без assetManager** (модель уже в приватных файлах).
- `connectedDebugAndroidTest` удаляет APK и данные после прогона — тесты с состоянием гоняют
  вручную (`adb install -r -t` + `am instrument`).
- Java-конфиг фичей не позволяет тюнить окно/преэмфазис; это не нужно в текущем скоупе.

## 7. Отложенные архитектурные решения (решаются при планировании)

1. **targetSdk** — фиксирование версии и вытекающее поведение (права, фоновая работа);
   minSdk (26) и R8 (отключён) уже решены.

Очередь оптимизаций после первого релиза (не в v2): чанкинг длинных записей (снимет лимит 180 с),
антиалиасный ресемплер (точнее распознавание с 44.1 кГц файлов), больше потоков,
предзагрузка модели при старте, собственная sherpa-сборка (NNAPI/точность),
fp32-энкодер, QNN-профилирование.

**Локальная LLM — запланированный этап стека (не в v2)** (решение 2026-11-07): после получения
каноничной расшифровки на устройстве работает локальная LLM — проверяет пунктуацию, исправляет
смысл/опечатки. Рамки: только офлайн (облако запрещено ТЗ), таймкоды и спикеры не трогаются,
исходный ASR-текст дублируется в лог для сравнения. Модель — компактная on-device (0.5–3B,
класс Qwen/Gemma), добавляется отдельным этапом после v2.
