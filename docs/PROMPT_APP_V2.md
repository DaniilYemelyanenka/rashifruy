# ПРОМПТ: Приложение «Расшифруй» — распознавание речи с диаризацией (создаётся с нуля)

> Промпт **самодостаточен**: предполагается создание нового Android-проекта с нуля, внешние файлы
> контекста необязательны. Решения заказчика зафиксированы в §«Принятые решения» и §«Решённые
> вопросы» (все закрыты; единственный открытый пункт планирования — targetSdk, см. Q10).
> Реализация — эпиками в порядке из §«Порядок реализации».

## Контекст (что берём как основу)

Приложение создаётся с нуля, но **движок и подход заранее проверены** на MVP-прототипе (он остаётся
в другом проекте как справочная база собранных фактов и граблей — см. §«Справка» ниже, знания
вынесены сюда, ссылаться на внешние файлы при планировании не нужно).

Реализуется **офлайн**-распознавание русской речи (GigaAM v3 RNN-T через sherpa-onnx, Java, без Compose)
+ диаризация говорящих + вывод с таймкодами + экспорт + запись с микрофона.

## Справка: проверенные факты и грабли sherpa-onnx (важно, до кода)

- Модель: `csukuangfj/sherpa-onnx-nemo-transducer-punct-giga-am-v3-russian-2025-12-16` (HuggingFace),
  файлы: `encoder.int8.onnx` (~224 МБ), `decoder.onnx`, `joiner.onnx`, `tokens.txt`. Важно:
  репозиторий `istupakov/...` НЕ совместим с sherpa-onnx v2.0.1 (3-input decoder, нет метаданных).
- AAR: `sherpa-onnx.aar` (v2.0.1) кладётся в `app/libs` + `implementation files('libs/sherpa-onnx.aar')`.
  В AAR уже скомпилированы: `OfflineRecognizer`, `OfflineSpeakerDiarization`
  (pyannote-сегментация + speaker-embedding + FastClustering) — выбирается всё диаризационное ИЗ AAR.
- `androidResources { noCompress += "onnx" }` — иначе ORT не примет файл из assets.
- Конфиг ASR: `OfflineModelConfig`: `modelType="nemo_transducer"`, `sampleRate=16000`, `featureDim=64`,
  `decodingMethod="greedy_search"`, `numThreads=4`, `provider="cpu"`;
  и главное: `new OfflineRecognizer(null, config)` — **не передавать assetManager** при файловых путях.
- Файлы модели копируются из `assets/gigaam/` в `filesDir/gigaam/` при первом запуске
  (~7 с на 224 МБ) с маркером-файлом.
- Шаг таймстемпов ≈ **40 мс** (хоп 10 мс × сабсемплинг 4). `result.getTimestamps()` — время **начала**
  каждого BPE-токена; длительность токена оцениваем `nextStart − start`, кап 0.6 с.
- Лимит модели ≈ **200 с** аудио (5000 кадров × 40 мс) — длиннее нельзя за один прогон.
- BPE: токены-продолжения слова НЕ начинаются с `▁`, новые слова начинаются. Склейка токенов
  **без добавленного пробела** — `▁` сам заменяется на пробел, иначе слова рвутся («соглас ные»).
- Java-`FeatureConfig` (v2.0.1) отдаёт только `{sampleRate, featureDim, dither}` — окно/преэмфазис/мел-диапазон
  не настраиваются (для их правки потребовалась бы своя сборка sherpa; НЕ в скоупе).
- Формат модели — ровно **16 кГц моно**; системный декодер MediaCodec даунмикс/ресемпл НЕ делает:
  конвертация — обязанность нашего кода (эпик F). Записи с микрофона (эпик E) это не касается —
  `AudioRecord` пишет сразу в 16 кГц.
- Профиль замеров на слабом x86_64-эмуляторе (3 vCPU): 139.4 с аудио → **31–36 с** на 4 потоках;
  энкодер 83% времени, джойнер 14%, декодер 2%; NNAPI готового AAR бесполезен (bug #2073) —
  эти цифры нужны только для спокойных ожиданий по производительности, не для оптимизаций в v2.
- Тест-инфраструктура: короткий `example.wav` (11.3 с, 16 кГц, без ресемпла) + длинный
  `ru_long_consonants.ogg` (139.4 с, 44.1 кГц, много естественных пауз; источник — Wikimedia Commons).
  ВНИМАНИЕ: `connectedDebugAndroidTest` **удаляет APK + данные приложения** после прогона —
  тесты с состоянием гонять только вручную: `adb install -r -t <apk-приложения> <apk-тестов>` +
  `adb shell am instrument -w -e class ... <pkg>.test/androidx.test.runner.AndroidJUnitRunner`.

## Целевое поведение (User Story)

1. Пользователь открывает приложение: сверху **«Расшифруй»** и под ним подпись **«от meevo»**,
   под ними кнопка **«Добавить файл»** (рядом кнопка-иконка **микрофона**) со статусом файла/записи,
   ниже — **фиксированное окно результатов** с внутренней прокруткой, под окном — кнопка **«Экспорт»**.
2. Автоматическое **разделение говорящих** (диаризация) с подписями «Спикер N» у реплик.
3. Временные метки реплик выводятся всегда.
4. Входные файлы: минимум **.mp3 и .wav** (плюс graceful для .ogg/.flac/.m4a), с **проверкой при добавлении**.
5. **Запись звука с микрофона** кнопкой: 1-е нажатие — старт, 2-е — стоп и передача дальше
   по пайплайну (валидация → декод → распознавание → диаризация → результат).
6. Итоговый результат нормализуется в **каноничную JSON-схему** (см. ниже); экспорт — TXT.

4. **Запрещено** подменять работу модели заранее подготовленной расшифровкой.

Следствие для реализации и проверок:
- весь пайплайн (fbank → encoder/decoder/joiner → диаризация → кластеризация) выполняется локально
  через sherpa-onnx (`OfflineRecognizer`, `OfflineSpeakerDiarization`) на устройстве;
- в коде не появляется: OkHttp/`HttpURLConnection`/Retrofit и любые сетевые вызовы в рантайме,
  `INTERNET`-permission в манифесте;
- в ресурсах/коде нет зашитых «эталонных» текстов, выводимых как результат
  (весь текст — только из `OfflineRecognizerResult`);
- записи с микрофона хранятся только в приватном каталоге приложения (`cacheDir`), наружу не выходят;
- критерий приёмки: `grep` по проекту на сетевые API/permission — 0 попаданий; сквозной тест проходит
  при отключённой сети эмулятора (`adb shell svc data disable`).

## Каноничная JSON-схема итогового вывода

```json
{
  "transcript": [
    {
      "speaker_id": "speaker_1",
      "start_ms": 1250,
      "end_ms": 4380,
      "text": "Добрый день!"
    }
  ]
}
```

- `transcript` — массив реплик в хронологическом порядке;
- `speaker_id` — строка `speaker_<N>`, N с 1, по кластерам диаризации;
- `start_ms`, `end_ms` — целые миллисекунды (int);
- `text` — строка, результат модели.

Правила реализации:
- это **внутренняя модель данных приложения**, не только экспорт: модель реплики —
  `int startMs/endMs + String speakerId`; сегментация, UI (`[mm:ss.ss – mm:ss.ss]` — форматирование
  из мс), лог-вывод и экспортёры читают ВСЕ из этой модели;
- конверсия сек→мс — ровно один раз, в точке сборки реплик (`Math.round(сек*1000)`), дальше только int;
- полный результат дублируется в лог (`Log.d("GigaAMTest", ...)`): строки JSON по одной на реплику
  (или весь массив одной строкой), без перехвата чужих логов;
- экспортёры (TXT сейчас, JSON/SRT — следующие) форматируют ИЗ этой модели, а не параллельно.

## Эпик A. Проверка файлов и форматная валидация (малый)

1. Whitelist расширений (`.mp3`, `.wav` минимум; `.ogg`, `.flac`, `.m4a` — graceful).
2. При добавлении: mime/размер; пробовать `MediaExtractor.setDataSource` — при ошибке показать
   «Файл не поддерживается/повреждён» (статус в UI + Toast + Log.d), не крашить приложение.
3. **Лимит длительности — единый 180 с** (решение 2026-11-07, запас до модельных ~200 с): файл/запись
   длиннее — отказ с сообщением «Длиннее 3 минут пока не поддерживается» (статус + Toast + Log.d).
4. Критерий приёмки: `.txt`/`.pdf`/битый файл — человеческое сообщение и без краша;
   `.mp3`, `.wav`, запись из эпика E — распознаются.
5. **TODO(MVP):** ограничение длительности — временное; вернуться при реализации чанкинга
   (минимальный MVP-этап, см. Q6 в §«Решённые вопросы»).

## Эпик C. Экспорт (малый)

1. «Экспорт» → диалог выбора формата: **TXT** (активен), JSON — заготовка (отключена, позже — почти
   бесплатно поверх каноничной модели).
2. SAF `ACTION_CREATE_DOCUMENT` с mime по формату (TXT: `text/plain`), suggested name
   `<имя_исходного_файла>.txt`; прав на хранение НЕ просить.
3. TXT: заголовок (имя файла/источника, дата, длительность, число спикеров) + реплики
   `[mm:ss.ss – mm:ss.ss] Спикер N: текст` — рендер ИЗ каноничной JSON-модели.
   **Формат времени единый `mm:ss.ss`** (решение 2026-11-07): одна функция-форматтер для UI
   и экспорта, JSON хранит целые миллисекунды.
4. Критерий приёмки: файл открывается вне приложения, содержимое == тому, что на экране.

## Эпик D. Диаризация говорящих (большой)

1. Включить `OfflineSpeakerDiarization`:
   - модели в assets (правила noCompress/копирования — как для основной модели):
     pyannote-сегментация (~2–3 МБ) + speaker-embedding (например 3D-Speaker/TitaNet, ~20–70 МБ)
     — конкретные модели выбрать из раздела docs sherpa-onnx speaker-diarization;
   - конфиг: `FastClusteringConfig`, `minDurationOn/Off` — подобрать на тестовом аудио;
   - `speaker_id` реплики = `speaker_<N>`, N = индекс кластера + 1.
2. **Отдельный компонент-анализатор `TranscriptAssembler` — «кто + что → обобщённая расшифровка»**.
   Вход — две структуры: (а) токены ASR с таймстемпами, (б) интервалы спикеров диаризации.
   Алгоритм (по токенам): каждому токену присваивается спикер интервала с наибольшим перекрытием
   его таймстемпа; при смене спикера реплика закрывается и открывается новая — тексты реплик
   собираются заново из подмножеств токенов (**иначе слова рвутся пополам**); токен, попавший
   к другому спикеру при слабом перекрытии (< 20% длины реплики), формирует отдельную реплику.
   start_ms/end_ms реплики = первый/последний токен реплики. Кластеров > 5 — объединение
   ближайших (решение Q7). Выход — **одна каноничная JSON-модель**, и никакой другой формы.
   Компонент не зависит от UI и sherpa (чистая функция над входными структурами) — покрывается
   unit-тестами на примерах: смена спикера на границе токена, пауза между репликами,
   перекрытие частично перекрывающихся реплик спикеров.
3. Отображение: «Спикер N» в сегментах UI, в логе и в экспорте; диаризация **всегда включена,
   переключателя в UI нет** (решение Q9).
4. Индикация: «Декодирование…» → «Распознавание…» → «Диаризация…» → «Готово».
5. Критерий приёмки:
   - **одноголосные** тестовые записи (Q8): путь диаризации отрабатывает без ошибок, 1 кластер →
     `speaker_1` у всех реплик; двухголосную тестовую запись добавить вручную позже;
   - дельта времени на 139 с записывается в метрики (базовая цифра — в §«Справка»).

## Эпик F. Ядро распознавания (базовый, обязателен сразу после B)

Предшествует эпикам A/E/C: без ядра нечего распознавать, нечего записывать и нечего экспортировать.

1. Копирование модели из `assets/gigaam/` в приватную папку с маркер-файлом; `noCompress "onnx"` (§«Справка»).
2. Фоновая инициализация после первого `onResume` (решение Q3): копирование → `OfflineRecognizer(null, config)`
   по конфигу из §«Справка»; статус «Подготовка модели…».
3. **Конвертация в формат модели (16 кГц моно)**: MediaCodec отдаёт исходные частоту и каналы —
   даунмикс в моно + ресемпл делает наш код; в v2 — линейный ресемпл как в прототипе,
   **TODO(точность): антиалиасный ресемплер** (см. вне-скоуп).
4. Token-based `Segmenter`: таймстемпы токенов → реплики каноничной JSON-модели (правило BPE §«Справка»).
5. Вывод: статус «Готово: N реплик», список `[mm:ss.ss – mm:ss.ss] текст` (формат из Q9/решения)
   в окне результатов; логи `Log.d("GigaAMTest", ...)`.
6. Критерий приёмки: короткий `example.wav` (11.3 с) и длинный `ru_long_consonants.ogg` (139 с)
   распознаются; времена — в пределах справочных (§«Справка»); таймкоды монотонные и в пределах
   длительности; реплики не пустые; слова не рвутся.

## Эпик E. Запись с микрофона (средний)

1. Кнопка-иконка микрофона рядом с «Добавить файл» (Material-иконка).
2. `RECORD_AUDIO`: запрос в рантайме при первом нажатии; отказ → статус «Нет доступа к микрофону»,
   ничего не стартует, приложение не крашится.
3. Во время записи кнопка «Добавить файл» disabled (решение Q2); во время пайплайна обе — disabled.
4. Запись: `AudioRecord` → **PCM 16 кГц, моно, 16-bit** — нативная частота модели, ресемпл НЕ нужен
   (грабля про потерю качества на ресемпл не воспроизводится, см. §«Справка»), писать WAV в `cacheDir`.
5. Поведение кнопки: 1-е нажатие — старт («Записывается… 00:xx», таймер в статусе), 2-е — стоп;
   файл автоматически идёт по пайплайну (эпик A валидация → декод → распознавание → диаризация).
   Отдельной отмены в v2 нет: только старт/стоп; перезаписать — начать новую запись.
6. Ограничения: мин. длительность 0.5 с («Слишком короткая запись»), макс. 180 с с автоостановом
   (текст-подсказка); все проверки — через эпик A.
7. Критерий приёмки: записанные 5 с распознаются; вывод в UI/логе по той же каноничной JSON-модели,
   что и для файла из пикера; `speaker_id` проставляется.
